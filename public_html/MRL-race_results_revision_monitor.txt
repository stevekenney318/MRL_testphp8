Purpose

race_results_revision_monitor.php is the planned second-stage race monitoring script for the Manlius Racing League (MRL) results pipeline.

Its job is not to watch the newest race live.
That is already handled by:
race_results_monitor.php

Instead, race_results_revision_monitor.php is intended to protect the integrity of the current season standings after race day by checking previously completed races for later ESPN revisions, such as:
- penalties
- points corrections
- bonus-point changes
- classification changes
- disqualifications
- any other post-race table adjustment

This script is a core data-integrity component, not an optional utility.

Related project source notes
- MRL-Roadmap.txt
- MRL-file-generation-and-versioning-standard.txt

Why this script is needed

The existing live monitor does a good job of:
- finding the newest race page
- waiting until a valid scoring-style table exists
- capturing snapshots
- avoiding false FINAL detection when the table is incomplete
- notifying when the first valid final table is found

However, it does not fully protect against this scenario:

1. race results are captured correctly on race day
2. weekly standings are published
3. segment standings and season standings update
4. ESPN changes a previously completed race later
5. MRL site does not notice unless manually checked

That is especially dangerous at:
- the end of a segment
- when prize positions are close
- when users assume the standings are official
- when a revision affects downstream totals

This revision-monitor script exists to close that gap.

High-level role in the architecture

Current live monitor
race_results_monitor.php

Primary job:
- monitor current/latest race
- run very frequently on race day
- detect when a new results page appears
- capture snapshots as the race evolves
- detect first valid final table

Planned revision monitor
race_results_revision_monitor.php

Primary job:
- monitor prior completed races in the current season
- run only a few times per day
- detect whether ESPN changed a previously stored race result
- save a new snapshot when meaningful change occurs
- notify immediately
- support downstream revision handling

Frequency / timing

This script is intended to run 2–4 times per day by cron.

Typical target cadence:
- morning
- midday
- evening
- late night

Goal:
- enough to catch late ESPN changes
- not so frequent that it creates unnecessary load or duplicate noise

This is not a race-day every-minute script.
It is a revision watcher.

Scope

The intended scope is:
- current season only
- previously completed points races
- races already known to the MRL system
- races with existing folders / prior snapshots

It should generally ignore:
- future races
- incomplete race stubs
- races outside the current season
- irrelevant folders
- non-points anomalies unless intentionally included later

Optional safeguard:
- skip the currently live/newest race if the live monitor is still actively handling it

Core functional objective

For each completed race in the current season, the script should answer:

Has the ESPN scoring table meaningfully changed since the last stored MRL snapshot for this race?

If yes:
- save a new snapshot
- log the revision
- alert immediately
- prepare for downstream recalculation / revision labeling

If no:
- do nothing
- no email
- no duplicate snapshot

Expected inputs

The script is expected to use the existing MRL race storage structure, especially:

/race_results/<year>/<race_folder>/

Typical files already present in a race folder:
- _meta.json
- final_table_hash.txt
- snapshot_YYYYMMDD_HHMMSSmmm.html
- snapshot_summary_YYYYMMDD_HHMMSSmmm.txt

It should also rely on:
- _year_index.json
- race folder naming already established by the monitor pipeline
- ESPN race result URLs already associated with those races

Existing behavior it should preserve

This script should not replace the current snapshot system.
It should build on it.

It must preserve the value of:
- raw HTML snapshots
- audit history
- timestamped history
- normalized scoring-table hashing
- existing helper structure
- deterministic file naming
- human-readable debug trail

This is an addition, not a redesign.

Revision detection philosophy

The revision monitor should focus on meaningful scoring changes, not cosmetic page changes.

That means it should prefer comparing the normalized scoring table rather than the entire HTML page.

Why:
- ESPN may change non-scoring HTML without affecting results
- ad / script / markup noise should not trigger revision alerts
- raw HTML still matters for audit, but not for classification

So the important comparison target is:
final_table_hash

or equivalent normalized scoring dataset derived from the race results table.

Real-world example that proved the need

A real revision case occurred for 2026 Bristol (R08).

Sequence:
- an initial final snapshot was captured on race night
- a later overnight snapshot was created
- an email alert was sent
- comparison showed that the ESPN table had changed

A specific example found in manual comparison:
- Chad Finchum changed from 0 points to 1 point

This proved:
1. revisions really do happen after initial publication
2. alerts must exist
3. revision monitoring is not theoretical
4. not every revision will affect MRL standings
5. MRL-specific revision classification is also needed later

Notification requirements

Notification is mandatory, not optional.

Whenever a real revision is detected:
- save new snapshot
- update revision state
- send email immediately

The philosophy is:
better to alert than silently miss a standings-affecting revision

Example subject style:
[MRL] REVISION DETECTED – 2026 R08 Bristol

Desired output artifacts when revision occurs

When a revision is detected, the race folder should gain a new timestamped snapshot, for example:
snapshot_20260413_030202493.html

Supporting data should update accordingly.

Potential related files or markers:
- final_table_hash.txt
- _meta.json
- under_review.flag
- snapshot_summary_*.txt

The exact downstream file set can evolve later, but revision detection should already fit the existing race-folder model cleanly.

Relationship to under_review.flag

A revision detector should integrate naturally with the current Pending Review concept.

When a revision is found, the script may create or preserve:
under_review.flag

This allows the UI to show:
⚠ Pending Review

until the revised result has been reviewed and accepted into the official MRL interpretation.

Downstream implications

A revision to an earlier race may affect:
- weekly winner for that race
- segment standings
- season standings
- tie order
- historical winners tables
- later adjusted totals if cumulative scoring changed

This is why the revision monitor is a prerequisite for the broader revision-handling model.

Relationship to future revision UI model

This script is intended to support a later user-facing revision model such as:
- Rev A
- Rev B
- Adjusted
- superseded snapshots
- revision history visibility

This script detects revisions.
Later UI work explains them to users.

Relationship to MRL-only impact classification

This script should detect race-table revisions.

Later, a second refinement layer should classify whether the revision actually affects MRL.

That future refinement is the planned:
- MRL-only driver extraction
- MRL-only scoring hash
- MRL-impact diff summary

This script is still necessary even before that layer exists.

Design constraints

This script should follow existing MRL architectural style:
- PHP 7.3 compatible
- deterministic behavior
- auditable output
- minimal moving parts
- use existing helper patterns where practical
- no unnecessary redesign
- no dependency on user history tables for current scoring logic
- work from current race snapshot system already in place

It should be easy to understand later by someone familiar with:
- race_results_monitor.php
- race_results_engine.php
- race_results_snapshot_helper.php
- race_results_team_helper.php

Desired behavior summary

On each run:
1. load current-season completed race list
2. iterate through previously completed race result pages
3. fetch current ESPN result page for each race
4. extract normalized scoring table
5. compare against latest stored scoring-table hash
6. if unchanged:
   - do nothing
7. if changed:
   - save new timestamped snapshot
   - update hash / metadata
   - mark race as under review if appropriate
   - notify immediately
   - prepare for downstream revision handling

In one sentence

race_results_revision_monitor.php is the MRL script that protects current-season standings from silently drifting out of sync with ESPN after race day by rechecking completed races for revised scoring tables, saving new snapshots when changes occur, and alerting immediately.
